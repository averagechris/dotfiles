# Advisor council

1. **Choose reviewers.** Ask for feedback before committing to a consequential design and before marking substantial work ready. Add an implementation review when a risky change is still easy to revise. The default panel is Opus 5.5, GPT-6.2 Sol, and Gemini 4 Carbon at high effort. Start with Opus for exploration or a quick check and add seats as uncertainty or stakes increase. Honor the user's requested lineup. Use every applicable [roster seat](references/models.md) when asked for a full council. Give each reviewer fresh context and collect independent, read-only findings before sharing other verdicts. Run reviews in parallel when possible.
2. **Frame the decision.** Give each reviewer the user's goal, acceptance criteria, constraints, and existing system behavior. Ask them to challenge the chosen design and identify a simpler way to meet the goal. For implementation review, provide the stable commit, PR diff, or working copy, including staged, unstaged, and relevant untracked changes. Include the callers, configuration, and tests needed to understand the behavior.
3. **Give reviewers the implementation.** Authorized reviewers can inspect the checkout directly. For external seats, inspect files before sharing and route OpenRouter seats through the [bundled runner](references/models.md#external-reviews) with approved diffs or excerpts. Keep external reviews running in pollable sessions until they finish or a task deadline applies. Exclude secrets and customer data. Ask each seat to identify the evidence it inspected and any missing context. Count reviews of design prose or pseudocode as design feedback.
4. **Check the failure that matters.** Prioritize security and correctness, then performance and simplicity. For credential or session changes, ask each implementation reviewer why the application needs to retain each credential. Trace tokens and bearer session identifiers through the actual backend, serializer, and configuration. Verify with synthetic values that ordinary access to a row, backup, or log reveals no reusable credential or bearer handle. Signing or encoding leaves data readable. Treat either exposure as a blocker.
5. **Verify findings.** Reproduce or check consequential findings against the implementation. Fix blockers and record the evidence for dismissed findings and any risk the user accepts. Before calling code ready, have two independent models review the final implementation unless the user explicitly requests a single reviewer for final signoff. After a material fix, apply the same reviewer minimum to the affected behavior and retain validated coverage of the rest.
6. **End the review.** A round includes reviewing, verifying the findings, and addressing them. End when the required reviews are complete and the work is ready or only nonblocking findings remain. Otherwise, allow up to three rounds by default. After the third round, continue only if the preceding round verified a fix to a consequential security, correctness, performance, or maintainability issue. Stop when two consecutive rounds resolve no consequential finding. Use the first applicable outcome.
   - **Stalled.** A verified blocker or a required review remains when the review stops. Report what is missing.
   - **Ready.** The required reviews are complete and all participating reviewers agree the work is ready.
   - **Converged.** The required reviews are complete and only nonblocking findings remain, with some reviewers withholding signoff. Report the remaining findings and disagreement.
7. **Ask for attention when it will help.** Before proactively escalating on the panel's behalf, ask each available reviewer assigned to the decision independently whether the user's attention would change the outcome. Escalation requires at least one affirmative vote and agreement from every available reviewer assigned to the decision. Keep dissenting reviewers in the panel. Report dissent and unavailable seats in ordinary task updates. Follow the task instructions for required authorization, direct user questions, and completion reports. Include the reviewed revision, scope, models, effort, and material disagreements. Get authorization before posting review results externally.

For an authorized defensive security review, use Gemini Carbon or the optional [Daybreak Blue seat](references/models.md#daybreak-blue-from-opencode) when the provider can receive the evidence. Use the bundled Codex CLI runner for Daybreak Blue from OpenCode. If a reviewer declines, report the gap and continue with any permitted defensive analysis.
