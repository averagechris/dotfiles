# rdny

rdny is the Rust browser automation CLI used on `suremac` and `tater`. It drives
Chrome-family browsers through the Chrome DevTools Protocol and keeps session
state between commands so agents can navigate, inspect, interact, capture
screenshots, record short videos, and attach to manually launched browsers.

## Package source

Hosts get rdny from the personal rolling SourceHut flake input, with locks
advanced to the v0.3.0 release revision:

```nix
inputs.rdny.url = "sourcehut:~averagechris/rdny";
```

The Home Manager module defaults `dotfiles.rdny.package` to
`inputs.rdny.packages.${system}.rdny` when that input is available.

## Home Manager module

Enable rdny with:

```nix
dotfiles.rdny.enable = true;
```

The module installs `rdny`, installs generated bash/fish/zsh shell completions,
can write `~/.config/rdny/config.toml`, can expose the CLI to OpenCode agents,
and can expose rdny's upstream bundled OpenCode skill declaratively. The generated config
mirrors rdny's user config schema:

```toml
[binaries]
chrome = [
  "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome",
]
ffmpeg = "/nix/store/.../bin/ffmpeg"
```

Module options cover rdny's current configuration and environment surface:

- `dotfiles.rdny.binaries.chrome.path` or `.package` selects the first
  `[binaries].chrome` candidate; `.fallbackPaths` appends ordered alternatives.
- `dotfiles.rdny.binaries.ffmpeg.enable` writes `[binaries].ffmpeg`; the default
  package is `pkgs.ffmpeg-headless`. All dotfiles ffmpeg consumers use the same
  headless output, avoiding competing `bin/ffmpeg` providers while retaining
  the command-line codecs and muxers needed for video assembly.
- `dotfiles.rdny.connect.default` and `.targets` write named `rdny connect`
  targets.
- `dotfiles.rdny.environment.stateDir` optionally exports `RDNY_STATE_DIR`.
- `dotfiles.rdny.environment.chromeArgs` optionally exports `RDNY_CHROME_ARGS`.
- `dotfiles.rdny.environment.maxDownloadBytes`, `.maxScreencastFrameBytes`,
  `.maxRecordingFrames`, `.maxRecordingSeconds`, `.maxRecordingBytes`, and
  `.minFreeDiskBytes` expose rdny's bounded download/recording environment
  controls. They default to `null`, preserving rdny's built-in 256 MiB download,
  8 MiB frame, 18,000 frame, 1,800 second, 512 MiB recording, and 256 MiB free
  disk defaults.
- `dotfiles.rdny.completions.enable` defaults to `true` and adds completions
  generated by `rdny completion bash|fish|zsh` to standard profile locations.
- `dotfiles.rdny.opencode.exposeTool` defaults to `true` and adds `rdny` to the
  generated OpenCode agent tool note when OpenCode is enabled.
- The module registers `rdny-browser` with the shared `dotfiles.agentSkills`
  renderer, sourcing it from the selected package. The skill is enabled by
  default; `dotfiles.agentSkills.rdny-browser` provides standardized per-skill
  `enable`, `patches`, and `extraText` controls documented in
  [`docs/opencode.md`](/docs/opencode.md).
- `dotfiles.rdny.settings` merges extra TOML, overriding generated values.

Binary precedence stays rdny-native: environment variables win first, then the
config file, then built-in fallbacks (`RDNY_CHROME`, `RDNY_FFMPEG`,
`RDNY_CONFIG`, and `RDNY_STATE_DIR` are all runtime escape hatches).

## Current upstream behavior

The v0.3.0 rdny release hardens managed sessions. `rdny start` now
launches Chrome behind an authenticated, owner-only local broker using
`--remote-debugging-pipe`; managed sessions no longer expose a DevTools TCP port.
External `rdny connect` targets remain the explicit loopback HTTP/WebSocket path.
Lifecycle state and artifacts use private transactional storage, command
timeouts share one deadline budget, downloads and recordings are bounded, and
machine output is available through global `--format human|json|jsonl` modes.
The release also bundles OpenCode skills, exposes generated shell completions,
and includes `rdny prop` for reading DOM properties from selected elements.

Configured Chrome executables are now ordered candidates. The module emits the
new array form even for one executable while upstream still accepts the old
single string for compatibility. Supplying this list replaces rdny's platform
discovery; nonexistent entries are skipped only when another configured entry
exists. `suremac` uses only Google Chrome so managed headless automation cannot
be mistaken for the interactive Helium app, while the Nix-managed Helium path on
`tater` is deterministic and needs no fallback.

## Host enablement

- `suremac` enables rdny, points `[binaries].chrome` only at the manually
  installed Google Chrome app for managed headless automation, enables ffmpeg
  for video assembly, and exposes rdny plus the `rdny-browser` skill to OpenCode
  agents. It also configures the non-default `helium` connect target and appends
  host instructions that reserve `rdny-helium` for explicit visible-browser
  requests.
- `tater` enables rdny, points `[binaries].chrome` at the Home Manager Helium
  package, enables ffmpeg, configures the same `helium` connect target, and
  exposes rdny plus the `rdny-browser` skill to OpenCode agents.

### suremac visible Helium workflow

`rdny-helium` connects every command to a dedicated graphical Helium profile:

```bash
rdny-helium pages
rdny-helium open https://example.com
rdny-helium click 'button'
```

The wrapper first reuses a healthy rdny connection or the loopback CDP endpoint
at `127.0.0.1:9333`. If neither exists, it starts visible Helium with that port
and the persistent profile at
`$XDG_DATA_HOME/rdny/visible-helium-profile` (falling back to
`~/.local/share/rdny/visible-helium-profile`), then connects through the isolated
rdny state directory under `$XDG_STATE_HOME`.

rdny cannot add CDP to an ordinary browser that is already running. Chromium
136 and newer also ignore remote debugging for the default browser profile.
Consequently, the wrapper deliberately starts a separate visible Helium instance
instead of trying to control or restart the user's ordinary Helium session. The
CDP port is loopback-only, but any process running as the same user can control
and inspect the dedicated browser while it is open; do not use that profile for
unrelated sensitive browsing.

On Linux, manually launch a configured browser binary with the same
`--remote-debugging-port=9333` flag and a non-default user data directory before
using the named target directly.

## Useful commands

```bash
rdny start --label agent
rdny status
rdny open https://example.com
rdny title
rdny --format json status
rdny html 'main'
rdny text 'h1'
rdny prop 'a' href
rdny js -
rdny screenshot page.png
rdny start-video
rdny stop-video recording.mp4
rdny stop
```

Use `rdny --state-dir <dir> ...` when you need an isolated session separate from
the default state directory.
